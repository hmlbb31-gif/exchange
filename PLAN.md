# MangaBuff Auto-Trader + Farm — план проекта

Дата: 2026-07-25. Основа: разведка сайта (Chrome) + разбор существующих проектов
`mangabuff-monitor-normal` (рабочий бот) и `mangabuff_personal_v0.4.5` (расширение).

Цель: телеграм-бот, который держит аккаунт «в сети», **автоматически принимает
только выгодные обмены** и **параллельно фармит дэйлики** (алмазы), с жёсткими
фильтрами, чтобы никогда не слить нужную/дорогую карту.

---

## 0. Что уже есть и переиспользуется

Из `mangabuff-monitor-normal` берём как образец (не трогаем оригинал, копируем
идеи в новый проект в рабочей папке):

- `mangabuff/client.py` — httpx + **обход DDoS-Guard** (куки привязаны к User-Agent),
  token-bucket рейт-лимитер, backoff на 426/429, детект «кука протухла».
- `mangabuff/cookies.py` — чтение cookies.txt (Netscape).
- `mangabuff/parser.py` — selectolax/regex-парсинг карт и рангов.
- Схема БД, aiogram-меню, systemd-деплой на Oracle.

Стек: **Python 3.11, aiogram 3, httpx, selectolax, SQLite, systemd** (тот же, что
уже отлажен и задеплоен).

## 2. Модуль обменника (ядро)

### Поток
1. Каждые N секунд: `GET /trades` → список входящих `trade_id`.
2. Для каждого нового: `GET /trades/{id}` → распарсить **что отдаю** и **что получаю**
   (список карт: `cardId`, ранг, номер экземпляра, сторона).
3. Оценить сделку (см. фильтры). Решение: **accept / reject / skip**.
4. `accept` только если сделка прошла ВСЕ фильтры. Иначе — оставить/отклонить.

### Правила выгодности (из твоих настроек)
- Один ранг: минимум **1:2 в мою пользу** (отдаю 1 — получаю ≥2 такого же ранга).
- Ранг выше: **1:1** допустимо.
- Настраиваемо на каждый ранг (X, S, A, B, C и т.д.).

### Фильтры — принцип **fail-closed** (главное правило безопасности)
> При ЛЮБОЙ неуверенности обмен **отклоняется**, а не принимается.
> Лучше пропустить выгодный трейд, чем слить нужную карту.

Отклоняем автоматически, если:
- Отдаваемая карта в **whitelist защищённых** (никогда не отдавать) — по `cardId`.
- Отдаётся карта, которой у меня **единственный экземпляр** (не дубль).
- Отдаётся **новая/редкая/дорогая** карта: цена с рынка выше порога, либо ранг ≥ порога,
  либо «ПП»-признак (уточнить определение — см. открытые вопросы).
- Не удалось **достоверно узнать цену** обеих сторон (рынок недоступен/пусто) → skip.
- Соотношение рангов/количества не проходит правило 1:2 / 1:1.
- В сделке есть незнакомый ранг/непарсибельная карта → skip.

### Оценка стоимости
- Кэш цен карт в SQLite: `card_id → (avg_price, min_price, last_price, updated_at)`.
- Обновление лениво: перед решением по трейду тянем `/market/card/{id}` для
  задействованных карт (с TTL, чтобы не долбить рынок).
- «Дорогая/дешёвая» = сравнение с настраиваемым порогом в валюте рынка (S).

### Whitelist / защита
- Таблица `protected_cards(card_id, reason)` — правится командами в ТГ.
- Плюс автозащита: всё, что дороже порога или редкого ранга, защищено по умолчанию.

## 3. Модуль фарма дэйликов (параллельно)

Отдельная «медленная» очередь задач, свой воркер, общий рейт-лимит с обменником.
Запуск раз в сутки (по расписанию) + докрутка недоделанного.

- **Шахта**: цикл `POST /mine/hit` до опустошения энергии/лимита (следим по `{ore}`),
  затем `POST /mine/exchange {diamonds}` для конвертации. Человеческие задержки
  между ударами (не мгновенно 100 раз).
- **Игры**: `/card-game/play` → `/card-game/claim`.
- **Квиз**: `/quiz/start` → `/quiz/answer`. Нужна **база вопрос→ответ** (собираем
  постепенно: на неизвестном вопросе логируем, отвечаем, запоминаем правильный).
- **Календарь**: `/balance/claim/{day}` — забрать награду дня.
- **Комментарии**: аккуратно, с задержками и лимитом (антиспам-риск высокий).
- **Реклама**: см. риски — вероятно, не автоматизируем на первом этапе.

Учёт: таблица `daily_runs(account_id, task, date, status, reward)` — чтобы не
делать дважды и видеть сводку «сегодня нафармлено X алмазов».

## 4. Мультиаккаунт и привязка

> Уточнено 2026-07-26: **обменник работает на 1 аккаунте** (мультиак ему не нужен).
> Мультиаккаунт (~10) нужен **только фарм-модулю дэйликов**. Поэтому у аккаунта
> есть роль (trade/farm), прокси привязывается в первую очередь к фарм-аккаунтам,
> а обменник ведёт один аккаунт без прокси.


- Таблица `accounts(id, tg_owner, label, cookie, user_agent, active, last_ok)`.
- Куки хранятся **зашифрованно** (Fernet, ключ в .env), не в git.
- **Health-check** каждые N минут: лёгкий GET, ловим редирект на `/login` → алерт
  «сессия аккаунта X сдохла», команда `/setcookie` для обновления.
- Один IP Oracle = вести себя как один обычный пользователь; при нескольких
  аккаунтах — либо разные IP/прокси (только к mangabuff), либо разнос по времени.

## 5. Телеграм-интерфейс

- `/accounts` — список, добавить/обновить куку, вкл/выкл авто-приём.
- `/trade on|off`, `/farm on|off` — переключатели по аккаунту.
- `/rules` — пороги 1:2/1:1 по рангам, порог цены.
- `/protect <cardId>` / `/unprotect` — whitelist защищённых карт.
- `/stats` — принято/отклонено/профит, нафармлено алмазов, сводка (как на твоём скрине).
- Уведомления: принят обмен (что на что), сдохла кука, сломался парсер, дневная сводка.

## 6. Риски и анти-бан

- **Главный риск: бан за автоматизацию.** Авто-приём и фарм почти наверняка против
  правил MangaBuff. Ведём себя по-человечески: рандомные задержки, дневные лимиты,
  не 24/7 на максимум, «тихие часы».
- **Рейт-лимит (426/429):** переиспользуем token-bucket + backoff из монитора.
- **Реклама** обычно требует реального просмотра рекламного видео (провайдер, а не
  просто POST). Автоматизация хрупкая и рискованная → на первом этапе пропускаем.
- **Смена вёрстки/роутов сайта:** парсеры и эндпоинты покрываем тестами на
  сохранённых страницах, падаем громко с алертом.
- **Куки протухают** (DDoS-Guard + UA): health-check + `/setcookie`.
- **fail-closed везде:** любая неопределённость в обмене = отказ.

## 7. Этапы

1. **Скелет проекта** в рабочей папке: config, БД, клиент (копия логики монитора),
   cookies, шифрование, aiogram-каркас, 1 аккаунт.
2. **Парсер обмена**: `/trades` + `/trades/{id}` → структура сделки. Тесты на
   сохранённом HTML.
3. **Оценщик цен**: `/market/card/{id}` → кэш цен.
4. **Движок решений** (fail-closed фильтры + правила 1:2/1:1 + whitelist).
   Сначала режим **«сухой прогон»**: бот пишет, что БЫ принял, но не жмёт accept.
5. **Авто-приём live** после проверки сухого прогона на реальных трейдах.
6. **Фарм**: шахта → игры → календарь → квиз (с базой ответов).
7. **Мультиаккаунт + ТГ-команды + сводки.**
8. **Деплой на Oracle** (systemd, бэкап БД), сутки наблюдения.

MVP = этапы 1–5 (обменник) + шахта из 6.

## 8. Решения (уточнено 2026-07-26) и что осталось доразведать

Ответы владельца:

1. **«ПП» = определяется по рынку** — не флаг первого принта/промо, а совокупный
   рыночный признак (много «Хочу» при малом числе лотов / много заявок). Значит
   текущий подход в `decision.py` + `cards.py` (рыночные сигналы) верный, отдельного
   флага карты не нужно.
2. **Политика рангов = «всё по выгоде + вето».** Жёсткой защиты рангов по умолчанию
   НЕТ: любой ранг можно отдать, если сделка выгодна и карта не ПП / не дороже порога.
   Защита — через whitelist и рыночное вето, а не через ранг. Приоритет на отдачу —
   низкие ранги (C/D/E), при желании и S. При этом пороги настраиваемы **по каждому
   рангу** (владелец сможет вручную защитить S/A/X через конфиг/команду).
   → **Нужна правка `config.py`/`decision.py`:** убрать дефолтную защиту X/S/A,
   оставить per-rank переключатель protected + fail-closed на неизвестный ранг.
3. **Валют несколько — способ сравнения ещё не решён** (владелец не уверен).
   → **Доразведать живьём:** какие валюты есть на рынке, можно ли их сравнивать
   между собой. До этого выгоду считаем по рангу, а цену/валюту используем только
   как вето «не отдавать дорогую» (в пределах своей валюты).
4. **Аккаунтов ~10, прокси нужны, список прокси у владельца есть.**
   → Мультиаккаунт + привязка прокси на аккаунт поднимается в приоритете (см. п.4):
   таблица `accounts` получает поле `proxy`, клиент — поддержку прокси на аккаунт,
   вести каждый аккаунт как отдельного пользователя со своим IP.

Ещё доразведать при реализации:

5. **Тело `/mine/hit`:** лимит энергии/кулдаун (сколько ударов реально в день) —
   снимем при реализации шахты под наблюдением.
6. **Квиз:** база ответов собирается автоматически (лог неизвестных → запоминаем).

## Замечание по безопасности проекта

Разведка велась только чтением (просмотр страниц и разбор публичного `manga.js`).
Ни один обмен не принят и не отклонён, шахта не тронута — все действия на аккаунте
делаешь ты, пока мы не согласуем «сухой прогон» и затем live-режим.
